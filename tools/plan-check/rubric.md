# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-fits-evidence | The plan's stated cause (its Cause/Diagnosis text, and the cause the plan comment claims) read step by step against the repro-evidence block, especially any control or comparison step (same input with one variable changed, a timing matrix, a "works when X" run). | Pass only if the stated cause explains every repro step, including the controls: for each step, the plan's cause predicts the result the repro actually recorded. Fail if any repro step shows the claimed cause absent while the bug still occurs, or present while the bug does not (the evidence rules that cause out). Also fail if the cause rests only on a thread claim or the plan's own assertion that the repro evidence never tests. A plausible cause the evidence contradicts is a fail, however confident it sounds. | required |
| bounded-named-scope | The plan's change and scope statements (In / Out / Not in scope, Files, Changes list) read against the issue body and the repro evidence. | Pass only if (a) the change is pinned to named files, functions or code sites that a stranger could open, not areas like "the parser" or "somewhere in the input stack", and (b) every listed change is needed to fix the behavior the issue and repro describe. These count as part of the fix, not scope creep: applying the same fix to sibling sites of the same defect in the same function or file, a regression test or doc line for the changed behavior, auditing for the same bug pattern, noting (not fixing) related problems for the PR, and a minimal CI or config edit that the plan shows is strictly required for the fix's own tests to run or pass in the repo's required checks (with quoted evidence such as an error transcript or a repo comment asking for it). New CI jobs, matrices, upgrades, or CI work the fix's own tests don't need are still creep. Fail if the plan leaves the location undecided ("X or Y, whichever is easier", "investigate first"), or if it bundles work the issue never asked for (refactors, migrations, new options or settings, redesigns, CI changes) next to the fix. | required |
| falsifiable-test-plan | The plan's test plan read against the repro-evidence block's steps and its Expected / Actual lines. | Pass only if the test names a concrete action (re-running specific repro steps, a named test case or command) and the specific observable result that would differ between the unfixed and fixed code (a color, output, exit code, timing, test assertion), so that if the fix failed, the test would visibly say so. Fail if the only success signal is generic ("run the full test suite", "nothing else breaks", "should feel fast") or is an outcome the current buggy code would also produce. | required |
| comment-honors-thread-and-policy | The candidate plan comment read against (1) the thread highlights: any explicit direction from a maintainer, owner, or collaborator (an isolated culprit, a requested approach, a request for testing, a pointer to an existing PR) and (2) the repo-facts block's contribution policy, especially any AI-use rule. | First list every explicit maintainer direction in the thread and every requirement the stated contribution policy places on comments or contributions. Pass only if the comment satisfies each item: it engages each maintainer direction (follows it, or says why the plan departs from it), and it meets each policy requirement (for example, an AI-use disclosure when the policy requires disclosing AI use; treat every package as AI-assisted work). Fail if the comment ignores or contradicts an explicit maintainer direction, or omits something the stated policy requires. If the thread has no maintainer direction and the policy states no requirement on comments, this check passes; do not invent conventions the package does not state. | required |

## Verdict rule

- **accept** only if every `required` check grades `pass`.
- **reject** if any `required` check grades `fail` or `unclear`.
- `unclear` (`?`) means the package does not contain enough to decide the check either way. For example, the plan names no cause at all, or the repro has no step that bears on the claimed cause. The grader may not fill the gap with its own guess about the codebase. `unclear` counts exactly like `fail` for the verdict, because a plan you cannot verify from the package is not ready to build from. The deciding evidence line must say what was missing.
- `preferred` checks (none yet) are reported but never change the verdict.
