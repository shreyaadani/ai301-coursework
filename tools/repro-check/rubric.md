# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record, read against the issue's stated target and the repo-facts block's bug-report template asks. | The report names the version or build of the software under test AND the platform facts this issue's behavior depends on (OS, shell, browser, driver, backend — whichever the issue implicates). Fails when there is no environment record at all, or when the issue is specific to a platform/driver the report never names. A record that is terse but complete passes. | required |
| steps-rerunnable | The repro report's steps and the inputs they name (config files, commands, sketches, sample data), read as a stranger with no access to the author's machine. | A reader outside the author's environment could assemble the inputs and run the steps: the starting state is given, the trigger is an exact command or action, and every input is shown inline, publicly obtainable, OR characterized specifically enough to rebuild an equivalent ("an env.yml with a valid dependencies list plus an unrecognized `category:` section" is rebuildable; verbatim quoting is not required). Fails when the reproduction rests on material nobody else can supply or reconstruct — an internal repo, a config whose relevant contents are never characterized — or when the steps skip the trigger itself. | required |
| artifact-present | The repro report's body: command output, console excerpts, logs, measurements, or described screenshots produced by the author's own run. | At least one artifact from the author's own attempt is shown. An honest cannot-reproduce passes here if it shows what its attempt actually produced. Fails on assertion-only reports ("I can confirm this", "I verified the race condition") that show no output from any run. | required |
| artifact-matches-issue | The artifact, read line by line against the specific behavior the issue describes: its error text, error class, exit code, or observable symptom. | The artifact exhibits the behavior the issue reports — OR the report states plainly that it could not reproduce and the artifact honestly shows the different outcome it got. Fails when the artifact shows an adjacent failure (a graceful validation error where the issue reports a crash, a compile error where the issue reports a path error, garbled output where the issue reports a terminal death) and the report presents it as the issue's behavior. Also fails when the artifacts show only that the tool runs. | required |
| deviation-acknowledged | The versions, platform, and syntax in the environment record and steps, compared with the version and configuration the issue targets or was confirmed on. | The environment matches what the issue targets, or the report names the difference explicitly (a stated version delta, a stated platform difference, a named difference in what the author's setup could not match). Passes when the issue names no target version. Fails on a silent deviation: an older version, a different platform, or an altered command/syntax tested as though it were the reported case. | required |
| conclusion-within-evidence | The report's expected/actual lines and any diagnosis sentence, read against what its own artifacts actually show. | Every claim the report makes is supported by an artifact it shows: a confirmation is backed by matching output, a cannot-reproduce is labeled as one, a cause is named only when something shown supports it. Fails on certainty the artifacts do not carry ("guaranteed reproducible", a root cause asserted with nothing shown) and on expected/actual stated backwards from the artifact. | required |
| claim-specific-and-honest | The candidate claim comment, read against the issue it is posted on. | The claim is about this issue in particular (it names what the author did, found, or will read next) and promises investigation only. Fails on interchangeable boilerplate that would fit any issue, on a bare "+1 / any updates?" with no stated intent, and on any promise of a fix, a delivery date, or a reserved assignment ("I will fix it within 2 days", "keep this issue reserved for me"). | required |
| disclosure-when-required | The repo-facts block's contribution-policy line, read for whether it requires disclosing AI assistance on issue comments; then the claim comment and repro report, read for a disclosure statement. | Passes when the policy states no disclosure requirement (no AI policy at all; a responsibility/understanding rule; a human-voice rule; or a disclosure ask the policy scopes to pull requests only). When the policy requires disclosure of AI assistance in a form that covers issue comments, passes only if a comment discloses the assistance. Treat every package as AI-assisted work: absence of disclosure under a covering policy is a fail, never an "unclear". | required |
| own-words | The claim comment and repro report against the repo-facts contribution policy, where that policy asks that comments to maintainers be written by the contributor rather than generated. | The comments read as a specific person writing about this issue — concrete detail, own phrasing — rather than generated filler. Never changes the verdict on its own. | preferred |

## Verdict rule

Accept if every `required` check passes. Any `required` check graded
`fail` produces reject. An `unclear` on a `required` check counts as
fail: proof that cannot be verified from the package is not ready to
post. `preferred` checks are reported but never change the verdict.

There is no partial credit and no third verdict: the package is either
ready to post (accept) or held for another pass (reject).
